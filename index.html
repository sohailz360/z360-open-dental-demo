03 · Inside the MCP server

What happens to every tool call

1 · Arrives from gateway

MCP over streamable HTTP, tool name + inputs

›

2 · Check token

Bearer token matched against stored SHA-256 hashes. Wrong or unknown → 401

›

3 · Find the practice

Token → connection: customer key, timezone, staff task user, rate limit

›

4 · Validate

Only allowed fields and parameters; Open Dental silently ignores typos, so we don't send any

›

5 · Call Open Dental

Paced per practice, 60 s timeout, unknown outcomes flagged

›

6 · Clear result

Always an explicit status (booked, conflict, practice_unreachable…) + what to do next

One service, many integrations

integrations-mcp
├─ /opendental/mcp 24 tools · live
├─ /charm/mcp · next
└─ /health state per integration

One broken integration answers 503; the others keep serving.

What a practice connection holds

  • Token hash (never the token itself)
  • The practice's Open Dental customer key
  • Practice timezone (Open Dental times have no offset)
  • Which Open Dental user creates staff tasks, and the default task list
  • Request pacing (min seconds between calls)

Where secrets live

  • AWS SSM: OD_DEVELOPER_KEY, OPENDENTAL_CONNECTIONS
  • Z360 stores only the practice's bearer token in its MCP server settings
  • Keys never reach the AI, prompts, logs or Z360's database
  • A practice never sees Z360's developer key

03 · Inside the MCP server

A retry never books twice

Every write, in order

1
Patient says yes

The AI reads the exact day, time and provider back first

2
Claim the operation_id

Same ID seen before → return the saved result, don't write

3
Pre-check Open Dental

Patient already has an overlapping visit → already_booked

4
Write

Only allowed fields, practice timezone applied

5
Read back

"Booked" only when Open Dental shows it

6
Log it, tagged [Z360]

So staff can tell AI actions from their own

Why: what we found when testing the real Open Dental API

Two identical bookings accepted

No conflict check or duplicate protection on Open Dental's side → we check first

Misspelled filters ignored

Full patient list comes back instead → strict parameter allowlist

API notes look like staff notes

Shown as "User" → every Z360 entry starts with [Z360]

Errors look like success

To the agent → every tool returns an explicit status field

03 · Inside the MCP server

One practice can never reach another's data

🔒 Private service

No public URL. The gateway allows exactly one private host:port, logged on every use.

🎫 Token per practice

Only its SHA-256 is stored. Strict 401, constant-time compare.

🧭 Identity from the token

The practice comes from the token, never from anything the AI sends.

🧱 Scoped per integration

An Open Dental token used on another integration's endpoint gets 401.

🔁 Rotation

New token, update the hash, redeploy; or run two tokens side by side for zero downtime.

🧪 Test data only

Sandbox license is test-only. Real patient data waits for the approved data path.

  • Update contact details and texting consent
  • Record recall outcomes and referral sources
  • Log communication; create staff tasks, tickets and leads

Nothing else is changed in Open Dental.
